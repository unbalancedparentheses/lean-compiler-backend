# Data-definition compatibility resource profile

This private candidate raises the module data-definition limit from 1,024 to 4,096. It addresses a concrete frontend-generated message catalog: 1,024 distinct strings plus a pointer table already exceeds the old cap. This is a bounded resource-profile expansion, not an unbounded QBE parity claim.

The implementation adds one compatibility constant and changes the validator's count guard. Native data remains bounded to 256 MiB, interpreter initialization to 1 MiB, parser input to 8 MiB and 600,000 tokens, and module parsing to 16,384 definitions. Certified-profile limits are unchanged. Name and relocation scans are unchanged; no unrelated lookup optimization was introduced.

The original pinned cproc frontend generated unchanged catalog IR with 1,024, 1,025, 2,048, 4,096 and 4,097 data definitions. Original QBE and independent platform C compilation both execute all catalog entries on all five targets: Linux ARM natively, Linux x86/RV through QEMU, Apple ARM natively and Apple x86 through Rosetta. There are 61,425 string/pointer checks per oracle family. Current pre-change LCB accepts 1,024 and refuses larger cases. The largest input is only 301,112 bytes. A first incomplete exploratory run lacked a host/guest assembly digest barrier and observed truncated assembly; its failure is retained as unqualified preflight evidence, superseded by the synchronized v2 run.

The final reusable helper uses data-only modules, so functions do not accidentally count toward these boundaries. At 1,024/1,025/4,096 definitions it checks every exported object's exact bytes and alignment, including the last object, across byte/half/word/long, floating bit-pattern initializers, zero fill, strings and pointer relocations with addends. It checks all three compiler modes and unchanged original QBE. Original QBE additionally executes 4,097 definitions; LCB explicitly refuses that count in all modes. A wrong final initializer must make the independent C caller fail. Duplicate-final-symbol, static TLS relocation and total byte-budget controls remain refused; the interpreter still refuses initialization beyond 1 MiB. Baseline/allocated/optimized assembly is identical for these data-only fixtures, and the 1,024 case matches the before snapshot exactly.

The diagnostic catalog validation and compile-resource reports were collected under concurrent regression load and are not performance benchmarks. Three 4,096-definition validations took approximately 0.091–0.110 s; one optimized ARM emission reported 0.24 s wall time and 47,185,920 bytes maximum resident set. No evidence here justified broadening the implementation to symbol-map changes.

No emitter changes, main-tree edits, or commits were made by this worker. The parent owns integration and the eventual actual-main qualification. Candidate identity and full source/helper/compiler/runner bindings are in the included reports and manifests. Compiled binaries remain in the bound private/mounted work directories; report claims must not be relabeled as another compiler identity without fresh qualification.

Final five-target matrix: 92,175 LCB object checks (5 targets × 3 modes × 6,145 objects), 51,210 unchanged-QBE object checks (including its admitted 4,097 case), 65 bounded rejection/budget checks and five detected wrong-last-entry mutations. The candidate also executes the unchanged 4,096-definition cproc catalog on Linux ARM in all three modes (12,285 string checks). All-five missing-tool emission controls and the default native CLI passed. Fresh units and the 147-entry proof audit passed. One initial unit syntax/build preflight is retained separately and superseded by the successful build.
